## Solana settlement and merchant records

- [x] **Solana USDC verifier and state machine:** Use a configurable Solana RPC provider and official USDC mint identity for each selected network; never trust token name, symbol, or logo. Server-side verification checks that the signature resolves to the intended transaction; execution succeeded; required confirmation/finality is achieved; token mint is correct; destination token account is owned by the merchant’s configured receiving wallet; amount matches request rules using mint decimals and integer arithmetic; signature has not credited another request; request is not already fulfilled; and expiry/acceptance policy is met. Explicit payment states are CREATED, AWAITING_PAYMENT, DETECTED, VERIFYING, CONFIRMED, UNDERPAID, OVERPAID, EXPIRED, FAILED, and REJECTED, with explicit legal transitions. Never set CONFIRMED before settlement criteria. Underpayment cannot automatically fulfill; overpayment follows explicit merchant policy. Expiry of the invoice remains distinct from whether later funds actually arrived; never silently ignore a late transfer. Include duplicate-signature protection, concurrency controls, retry handling, transaction reconciliation, and subscriptions if supported with reliable polling fallback. Never claim confirmation when RPC cannot establish status.
- [x] **Orders and payment request lifecycle data:** Maintain orders with order ID, description, expected amount, currency, payment-request ID, payment status, confirmed signature, created/updated timestamps, and workflow status. Inspect the full lifecycle for each payment. Update an order through server-side business logic only after successful verification. Use database transactions/equivalent concurrency control when recording verified payment and updating the matching order. Store money in integer base units or precise decimal representation, never floating point.
- [ ] **Verifiable receipts:** A confirmed settlement produces a clean shareable, printable, downloadable receipt with unique receipt number, merchant identity, payment-request ID, order reference, USDC amount, Solana network, verified transaction signature, receiving wallet address, confirmation timestamp, relevant Solana explorer link, verification status, and receipt-creation timestamp. Receipts are immutable snapshots of confirmed facts. Administrative correction preserves the original audit record and adds a clearly documented correction event. Do not call an unconfirmed transaction paid or generate its paid receipt. **Implemented:** confirmed immutable receipt snapshots, public share/print/download, and verified transfer signatures. **Still open:** no administrative correction-event flow is exposed; snapshot facts are never edited.
