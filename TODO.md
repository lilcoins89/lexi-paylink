## Solana settlement and merchant records

- [x] **Solana USDC verifier and state machine:** Use a configurable Solana RPC provider and official USDC mint identity for each selected network; never trust token name, symbol, or logo. Server-side verification checks that the signature resolves to the intended transaction; execution succeeded; required confirmation/finality is achieved; token mint is correct; destination token account is owned by the merchant’s configured receiving wallet; amount matches request rules using mint decimals and integer arithmetic; signature has not credited another request; request is not already fulfilled; and expiry/acceptance policy is met. Explicit payment states are CREATED, AWAITING_PAYMENT, DETECTED, VERIFYING, CONFIRMED, UNDERPAID, OVERPAID, EXPIRED, FAILED, and REJECTED, with explicit legal transitions. Never set CONFIRMED before settlement criteria. Underpayment cannot automatically fulfill; overpayment follows explicit merchant policy. Expiry of the invoice remains distinct from whether later funds actually arrived; never silently ignore a late transfer. Include duplicate-signature protection, concurrency controls, retry handling, transaction reconciliation, and subscriptions if supported with reliable polling fallback. Never claim confirmation when RPC cannot establish status.
- [x] **Orders and payment request lifecycle data:** Maintain orders with order ID, description, expected amount, currency, payment-request ID, payment status, confirmed signature, created/updated timestamps, and workflow status. Inspect the full lifecycle for each payment. Update an order through server-side business logic only after successful verification. Use database transactions/equivalent concurrency control when recording verified payment and updating the matching order. Store money in integer base units or precise decimal representation, never floating point.
- [ ] **Verifiable receipts:** A confirmed settlement produces a clean shareable, printable, downloadable receipt with unique receipt number, merchant identity, payment-request ID, order reference, USDC amount, Solana network, verified transaction signature, receiving wallet address, confirmation timestamp, relevant Solana explorer link, verification status, and receipt-creation timestamp. Receipts are immutable snapshots of confirmed facts. Administrative correction preserves the original audit record and adds a clearly documented correction event. Do not call an unconfirmed transaction paid or generate its paid receipt. **Implemented:** confirmed immutable receipt snapshots, public share/print/download, and verified transfer signatures. **Still open:** no administrative correction-event flow is exposed; snapshot facts are never edited.

## Workflows, notifications, and operational reliability

- [x] **Configurable workflow engine and PayLink Autopilot:** Support triggers for payment request created, payment detected, payment confirmed, payment underpaid, payment expired, and verification failed. Support actions to generate a receipt; mark an order paid; send Telegram notification; send email notification; send a signed merchant webhook; redirect the customer after verified settlement; and record a payment-history event. Support conditions, execution history, per-action status and failure reasons, and retry controls. Example confirmed flow can generate a receipt, mark an order paid, and send Telegram/email only when the verified amount satisfies the request. Never fulfill on transaction submission. Persist jobs across restarts and implement idempotency keys, bounded retries, exponential backoff, and failed/dead-letter view. Retrying a notification does not credit/fulfill again. Plain-English workflow configuration converts an instruction to structured triggers, conditions, and actions, validates it, displays the proposal, and requires merchant confirmation before activation. AI may draft/explain only; deterministic code owns verification and execution. If no LLM is configured, provide a deterministic template-based builder and do not claim AI is connected. **Delivery semantics:** payment settlement, order/receipt fulfillment, and workflow-history events are idempotent; external Telegram/email/webhook delivery is at-least-once and may repeat after an ambiguous provider timeout. Webhook receivers should deduplicate the stable delivery key.
- [x] **Isolated workflow simulation:** Merchants can test a workflow with clearly labelled simulated events before activation. Show expected actions, conditions, and possible failures without submitting real transactions or sending real notifications. Simulation must not accidentally execute real payment actions.
- [x] **Telegram/email settings and delivery attempts:** Merchants can configure Telegram/email notifications. Telegram bot credentials stay securely server-side; provide bot setup instructions and validate chat destination; only send after the required event is verified. Use a configurable email provider with templates for payment received, underpaid payment, expired invoice, and workflow errors. Provider keys stay server-side. Include reference, amount, status, and receipt link where appropriate. Persist delivery attempts and allow retry without repeating payment fulfillment. **Unconfigured:** live provider delivery was not exercised because merchant/provider credentials are not configured in this run.
- [x] **Signed merchant webhooks and delivery operations:** Support configurable HTTPS webhook destinations, event subscriptions, HMAC signatures, timestamp/replay protection, attempts and response codes, retry controls, endpoint validation, and protection against SSRF, private-network targets, and unsafe redirects. Build an operational reliability view showing verification delays, failed workflow actions, pending reconciliation, notification delivery failures, duplicate-event suppression, and retry status. **Limitation:** process-local rate limits must be replaced with a shared store before horizontally scaled production.
- [x] **Tamper-evident payment history:** Preserve ordered per-request audit events for request creation, payment detection, verification checks, state changes, workflow decisions, receipt creation, notification delivery attempts, errors, and retries. Use canonical event serialization and cryptographic hash chaining to make tampering detectable. Describe a hash chain as tamper-evident, not proof that source records were truthful or publicly immutable.
